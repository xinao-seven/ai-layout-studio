# 给 Agent 接入画房间能力:add_room 工具(第 10 个工具)

## Context

目前 Agent 有 9 个工具(M3 的 7 个家具/问答工具 + M4 的 auto_layout/verify_layout),但**不能建房间** — 用户说"帮我画一个 4×5 米的卧室"时,LLM 只能建议用户手绘。服务端 `room.add` PatchOp、proposal 确认链、`invalid_polygon`/`room_too_small` refusal 码、Shapely 多边形校验全部已存在(手动路径在用),只缺:面向 LLM 的工具定义、operation 层纯函数、以及客户端对房间提案的幽灵渲染(目前 pendingOverlay 只输出 item diff,房间提案确认前完全不可见)。

**范围**:本次只做"新建房间"(单次一个房间)。修改/删除房间工具、门窗随房间一起提案、eval 用例扩展留作后续。

## 设计要点

- **工具名**:`add_room`,与 `add_item` 命名一致,kind="write",走标准 proposal→confirm 链。
- **输入**:LLM 直接输出多边形顶点(`polygon: list[Vec2]`,米,≥3 点)。这是对系统提示词"never output raw coordinates"的**唯一例外**,需同步改 prompt(room 几何没有 relation 体系,LLM 必须给坐标;服务端会吸附+校验兜底)。
- **服务端 operation**(`plan_add_room` 纯函数,遵循 ADR-0002 三层范式):
  1. 顶点吸附到 `rules.GRID_SNAP`(0.1m,与刚上线的手绘吸附一致)→ snap 后去重相邻/首尾重复点(<3 点 → `invalid_polygon` refusal);
  2. `ensure_ccw` 自动纠正绕向 → `validate_polygon(min_area=rules.min_room_area)`(复用 `app/geometry/polygon.py`,GeometryError → refusal);
  3. mint `new_id(IdPrefix.ROOM)`,name 缺省 `房间 {n}` → 产出 `[RoomAddOp]` + `document_after`(apply_ops 带 validate,与 place_add 一致)。
  4. 不做房间重叠检查 — 与手动 `room.add` 路径行为保持一致(服务端从不校验房间互斥)。
